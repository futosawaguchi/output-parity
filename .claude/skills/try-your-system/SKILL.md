# 自分のシステムを試せるようにする（設定を一緒に書く）

このツールは、言語・ライブラリ・実行環境のバージョンを上げる前と後で同じ入力から出した出力を比べる。比べるには、題材ごとに設定ファイルが1枚要る。
このスキルは、その1枚を本人と一緒に書き、**Claude を呼ばずに1回流して動く**ところまでを受け持つ。判定（Claude に送る）は、本人が中身を見て決めてから。

## 守ること（先に本人に伝える）

- ✍️ **書くのは `targets/<名前>/` の中だけ。** 本人のソースは読むだけで、1文字も書き換えない（ツールも、直し方を当てるのは写しの `work/` だけ）。`targets/` は `.gitignore` 済みなので、社内のパスや名前を書いても公開されない
- 🔌 **本番に触らない。** 本番のサーバ・本番の DB・本番の URL を設定に書かない。ソースはローカル環境に置いた写しを使ってもらう。DB を使うプログラムは、試す用の DB（SQLite のファイルの写し、または本人が用意した試す用の DB）につなぐ
- 🙈 **読む前に、読んでよい範囲を本人に確かめる。** このスキルでソースを読むと、その中身は Claude Code を通して Claude に送られる。`.env`・鍵・証明書・パスワードの入ったファイルは開かない（名前と、どこで読んでいるかだけ見る）
- 📨 **`claude.send` は本人が選ぶ。** 既定は無い。勧めるのは `"none"`（何も送らずに比べる）から始めること。`output`・`output-and-source` に変えるのは、本人が結果を見て、送ってよいと決めてから（guide/safety.md の「Claude に送るもの」）
- 🏷️ 入力の `id`・`label`・`description` は画面に出て、Claude にも渡る。**期待する判定が分かる名前にしない**（❌ `broken-total` ⭕ `case-3`・「3月分の請求」）

## 1. 聞く（まとめて1回。分からないものは「分からない」でよい）

1. ソースはどこにあるか（ローカル環境の写しか）。読んでよいフォルダ、読んではいけないフォルダ
2. 比べたいのは何の出力か（帳票の PDF・CSV やログ・画面）。いま、どの入力で動かしているか（データのファイル・URL のパス・コマンドの引数）
3. 旧と新の環境（例 PHP 7.4 → 8.5）。それぞれの実行ファイルのフルパス（`which php` では足りない。旧のバージョンを入れていなければ、後の「旧の環境が無いとき」）
4. DB・外への送信（メール・外部 API）を使うか
5. 本番の実行環境の設定で、出力に効きそうなもの（PHP の `php.ini` の `date.timezone`・ロケール・拡張など）。ローカル環境と違えば、設定の `args`（例 `"-d", "date.timezone=Asia/Tokyo"`）か `env` で本番に寄せる。本人が分からなければ、旧と新の両方で `php -i` の `date.timezone` などを見て、ローカル環境の値を本人に伝える（出力に日時があるなら特に）

## 2. 読む（本人が許した範囲だけ）

- 入口を探す: README・`composer.json`・`requirements.txt`・`public/index.php`・`main.py`・`bin/` など
- 出力を作る場所: PDF を書く行（TCPDF の `Output(` など）・ファイルを開いて書く行・`echo`/`print` で標準出力に出しているか
- 入力の形: 引数・データのファイル（どのフォルダに何件あるか）・画面なら URL のパスと `?id=` のような値
- 環境変数と `.env` を読む箇所（`getenv`・`$_ENV`・`os.environ`・`load_dotenv`）。⚠️ `load_dotenv()` は親のフォルダまで `.env` を探すので、写し（`work/` はこのリポジトリの中）から動かすと**ツールの `.env`（API キー）を読めてしまう**。そういうプログラムは、必要な値を設定の `env` で渡し、ツールの `.env` を使わない運用にしてもらう
- DB の接続先（ホスト名・ファイル名）。本番を指していたら、設定の `env` で試す用に向けられるかを見る
- **本番の環境に依存していて、ローカル環境ではそのまま動かない箇所**: 本番サーバの絶対パス（`/home/...` のテンプレート・設定ファイル）・本番のホスト名・本番にしか無いファイル。見つけたら、5 で流す前に本人に伝える（下の「ローカル環境で動かない箇所があるとき」）
- 毎回変わる値（日時・ID・乱数）を出しているか。ツールが新の環境で2回流して見分けるので、設定には何も書かなくてよい（本人にそう伝える。2回目は1回目の終了から1秒あけるので、秒までの日時も見分けられる。旧と新がたまたま同じ秒に出た入力では、日時は差にならず、落とした差にも出ない）

## 3. 型を決める

| 当てはまるもの | `run.type` | 例 |
|---|---|---|
| コマンドで動かすと出力が出る（引数・データのファイル） | `command` | `samples/estimate/`（PDF）・`samples/worklog/`（Python・CSV） |
| ブラウザで開く Web アプリ | `web` | `samples/bookshop/`（PHP の内蔵サーバ・SQLite） |
| 旧と新の出力がもうファイルである（旧の環境はもう動かせない） | `files` | guide/config.md の「ファイル型」 |

- 出力の形式: `pdf`・`text`（CSV・ログ・JSON・標準出力）・`html`（画面）。Shift_JIS などは `output.encoding`。1つの題材に形式が混ざるとき（画面の中に CSV の書き出し）は、その入力だけ `cases[].output`（`samples/bookshop/` の `export`）
- Web 型は、ツールが `127.0.0.1` に旧と新のサーバを立てる。設定に URL は書けない（パスだけ）。ログインはツールではできないので、ログインが要る画面は試す環境だけで外してもらう
- **旧の環境が無いとき**: 旧のバージョンをローカル環境に入れる（Homebrew・各言語のバージョン管理）か、昔の出力が残っていればファイル型で比べる。Docker で動かす場合も、設定の `command` はローカル環境から呼べるフルパスにする

## 4. 書く

- 置き場所は `targets/<名前>/parity.config.jsonc`（名前は英小文字・数字・`-`）。キーの意味の正は **guide/config.md**。一番近い `samples/*/parity.config.jsonc` を写して直すのが早い
- `source` は本人のソースの場所（設定ファイルからの相対か絶対パス）。⚠️ `work/` の中や、設定ファイルのあるフォルダそのものを指さない（その下に作った写しはよい）
- **ローカル環境で動かない箇所があるとき**（本番の絶対パスなど）: 本人の元のソースは書き換えず、`targets/<名前>/app/` に**その箇所を含むファイルだけ**を写して差し替え、ほかは元へのリンクにして、`source` をそこに向ける。差し替えたのが何行かを、写したファイルの先頭と設定のコメントに書く。本番にしか無いファイル（帳票のテンプレートなど）は、本人に取ってきてもらい `targets/<名前>/` に置く（代わりのものを作ると、それを読むところの違いを見逃す）。リンクするのは動かすのに要るフォルダだけ（DB のダンプ・パスワードのファイル・`.git` はリンクしない）。⚠️ 公開の場では「差し替えた写しで試した」と正直に言う
- 入力は**少なく始める**: 2〜5 件。ふだんの入力・境目の入力（0 件・空欄・長い名前）・昔問題が出た入力。データのファイルが10件を超えるか、これから増えていくなら `caseGroups` の `each.file` で1行にまとめる（ふだんの動かし方と引数の形が変わるが、それでよい）。⚠️ `each.file` が探すのは `run.cwd` の**直下だけ**（`"data/*.json"` とは書けない）→ `run.cwd` をデータのフォルダにし、`args` のプログラムを `../bin/…` のように相対で書く
- 出力の受け取り方: プログラムが引数のファイルに書くなら `"output": { "from": "file" }` と、`args` のその位置に `{output}`（ツールが出力ファイルのパスに置き換える）。標準出力に出すなら `"from": "stdout"`
- `fixes`（直し方を当てるか）: 既定の `"apply"` は、`source` を丸ごと写した `work/<名前>/`（このリポジトリの中・`.gitignore` 済み）で動かし、直し方をそこに当てて確かめられる。⚠️ **`.env` などもそのまま写る**（Claude には読ませない・送らないが、ファイルとしてはこのリポジトリの中に置かれる）。写したくなければ `"suggest-only"`（その場で動かし何も書かない。直し方は提案だけ）。どちらにするかは本人に選んでもらう
- 依存（`vendor/`・`node_modules/`）が要るなら `run.needs` に書く（無ければ実行の前に、取り方つきで止まる）
- PHP で PDF を標準出力に書くなら `args` に `"-d", "display_errors=0"`（警告が PDF の先頭に混ざる）
- 外へ送るプログラム（メール・外部 API）は、試す環境で止める設定（環境変数など）を `env` で渡してもらう。⚠️ ツールはそれを止められない
- 書いたら、どの行が何のためかを短いコメント（`//`）で残す（本人があとで直せるように）

## 5. Claude を呼ばずに流して確かめる

```sh
npm run samples -- --subject <名前>       # --judge は付けない（Claude を呼ばない）
```

- 止まったら、出たメッセージの「次に何をすればいいか」に従って設定を直し、もう一度流す。よくあるもの:
  - 「設定ファイルの … がありません」→ キーの書き漏れ（guide/config.md）
  - 「実行に要るものがありません」→ `run.needs` のもの（composer install など）
  - 「設定された実行コマンドが見つからないか、実行できません」→ `command` のフルパス
  - どの入力も「出力なし」→ 出力の場所（`{output}` を `args` に入れたか・`output.from`）。`runs/<id>/<入力>/new/stderr.txt` にプログラムのエラーがある
- 流れたら、入力ごとの結果を本人に見せる。差が無ければ「無害（機械）」、出力が出なかった入力も機械で決まり（新でだけ出なければ「壊れている（機械）」）、残った差がある入力は「判定: なし」と出る。**ここで判定はしていない**（Claude を呼んでいないので、決まるのは機械で分かるものだけ）
- ⚠️ `work/<名前>/` はツールの作業用の写し。消してよい

## 6. 本人に報告する

- 書いたファイルと、本人に決めてもらったこと（読んだ範囲・`claude.send`・入力の選び方）
- 流した結果（何件・差なし・残った差・出力なし）と、気になったこと（毎回変わる値が多い・出力なしの入力がある、など）
- 次の一手:
  - 画面で見る: `npm run dev` → `http://127.0.0.1:3000/check?subject=<名前>`
  - 判定させるなら、送るものを本人が読んでから `claude.send` を変える（guide/safety.md の「Claude に送るもの」）。そのあと `npm run samples -- --subject <名前> --judge` か画面の「実行して判定する」
  - 入力を増やす（境目の入力・昔問題が出た入力）
